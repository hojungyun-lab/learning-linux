# 02. 프로세스 생명주기 및 시그널(Signal) 제어

## 🎯 학습 목표 (Goal)
- Linux 커널의 프로세스 상태 코드(`R`, `S`, `D`, `Z`)의 차이와 발생 원인을 정확히 이해합니다.
- 운영 환경에서 `kill -9`를 무분별하게 사용하지 말아야 하는 이유와 `SIGTERM(15)` 기반 Graceful Shutdown(정상 종료) 원리를 파악하고, 생성된 **좀비(Zombie) 프로세스를 추적하여 안전하게 정리하는 방법**을 실습합니다.

---

## 💡 핵심 개념 (Core Concepts)

### 1. 프로세스의 4대 상태 코드 (Process States)
커널 프로세스 스케줄러는 프로세스를 다음 중 하나의 상태로 관리합니다:

| 상태 코드 | 명칭 | 설명 및 시스템 엔지니어링 관점의 의미 |
| :---: | :--- | :--- |
| **R** | Running / Runnable | CPU에서 실행 중이거나 CPU 실행 큐(Run Queue)에서 대기 중인 상태. 이 프로세스 수가 CPU 코어 수를 초과하면 로드 애버리지가 상승합니다. |
| **S** | Interruptible Sleep | 이벤트(I/O, 네트워크 응답, 타이머)를 기다리는 유휴 상태. 시그널을 수신하면 즉시 깨어납니다. (대부분의 데몬 프로세스 상태) |
| **D** | Uninterruptible Sleep | 디스크 블록 읽기/쓰기, NFS 응답 등 중요한 커널 공간 작업을 수행 중인 상태. **시그널(`SIGKILL` 포함)을 무시합니다.** D 상태 프로세스가 많으면 스토리지 병목을 의심해야 합니다. |
| **Z** | Zombie (`<defunct>`) | 자식 프로세스가 `exit()`을 호출하여 실행을 마쳤으나, 부모 프로세스가 `wait()` 또는 `waitpid()`를 호출하여 자식의 종료 코드를 수거하지 않아 커널 프로세스 테이블에 남아 있는 상태. |

### 2. 왜 좀비 프로세스는 `kill -9 <PID>`로 죽지 않는가?
좀비 프로세스는 이미 코드 실행을 멈추고 메모리 공간(텍스트, 힙, 스택)을 반환한 상태입니다. 커널의 `task_struct` 테이블에 **종료 코드와 PID 정보**만 남아 있는 "유령" 객체이므로 시그널을 받아 처리할 프로세스 엔터티 자체가 존재하지 않습니다.
- **해결책**:
  1. 부모 프로세스에게 `SIGCHLD` 시그널을 전달하여 자식의 상태를 회수하도록 유도하거나,
  2. 부모 프로세스를 정상 종료(`SIGTERM`)시킵니다. 부모가 종료되면 자식 프로세스는 **PID 1 (init/systemd)**의 고아 프로세스로 입양(Adopt)되며, PID 1이 즉시 `wait()`를 호출하여 좀비를 완전히 소멸시킵니다.

### 3. 주요 POSIX 시그널 비교
| 번호 | 시그널 이름 | 기본 동작 | 프로세스 핸들링(Catch/Trap) 가능 여부 | 권장 사용 시점 |
| :---: | :--- | :--- | :---: | :--- |
| **15** | `SIGTERM` | 정상 종료 | **가능** (핸들러 등록 가능) | **[기본값]** 진행 중인 트랜잭션 및 DB 커넥션을 정리 후 종료 |
| **9** | `SIGKILL` | 강제 즉각 사살 | **불가능** (커널이 즉각 메모리 회수) | `SIGTERM` 후 일정 시간(Grace Period) 내 무응답 시 최후의 수단 |
| **1** | `SIGHUP` | 터미널 연결 끊김 / 설정 재로드 | **가능** | Nginx 등 데몬의 설정 파일 무중단 재적용 |
| **2** | `SIGINT` | 인터럽트 (Ctrl + C) | **가능** | 대화형 세션에서 실행 중단 |

## 🛠️ 실습 코드 (Hands-on)

### Step 1. 프로세스 트리 및 계층 구조 파악
컨테이너 내부에서 현재 실행 중인 프로세스들의 부모-자식 관계를 시각적으로 확인합니다.

```bash
# linux-lab 컨테이너 내부에서 실행
pstree -apnh
```

*출력 예시:*
```text
bash,1
  └─pstree,12 -apnh
```

### Step 2. 포그라운드 프로세스와 백그라운드 작업 제어
작업 제어(Job Control)를 위한 시그널 전달 메커니즘을 테스트합니다.

```bash
# 1. 60초 동안 대기하는 백그라운드 작업 실행
sleep 60 &

# 2. 작업 목록 및 Job ID 확인
jobs -l

# 3. 백그라운드 프로세스의 PID를 확인하고 SIGTERM 시그널 전송
kill -15 %1

# 4. 프로세스가 정상 종료되었는지 확인
jobs
```

### Step 3. 실전 장애 재현: 좀비 프로세스 대량 생성
`chaos-target` 서버의 장애 주입 엔드포인트를 호출하여 의도적으로 좀비 프로세스를 5개 생성합니다.

```bash
# linux-lab 컨테이너에서 실행
curl -X POST "http://chaos-target:8000/chaos/zombie?count=5" | jq .
```

*응답 예시:*
```json
{
  "status": "zombies_spawned",
  "created_pids": [15, 16, 17, 18, 19],
  "message": "부모 프로세스가 waitpid를 호출하지 않아 자식 프로세스가 좀비(Z 상태)가 되었습니다."
}
```

### Step 4. 좀비 프로세스 추적 및 진단
좀비 프로세스는 일반적인 CPU 점유가 없으므로 `top`에서는 간과하기 쉽습니다. 전용 옵션으로 추적합니다.

```bash
# 1. 시스템의 Z(Zombie) 상태 프로세스만 필터링 출력
ps -eo pid,ppid,state,comm | awk '$3=="Z"'

# 2. 타깃 컨테이너의 프로세스 상세 조회
# COMMAND 열에 <defunct> 표기가 붙어 있는지 확인합니다.
ps aux | grep defunct
```

*출력 예시:*
```text
USER       PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
root        15  0.0  0.0      0     0 ?        Z    13:20   0:00 [python3] <defunct>
root        16  0.0  0.0      0     0 ?        Z    13:20   0:00 [python3] <defunct>
root        17  0.0  0.0      0     0 ?        Z    13:20   0:00 [python3] <defunct>
```

### Step 5. 좀비 프로세스 정리 실험
좀비 프로세스의 PID(예: 15)를 직접 강제 종료해 봅니다.

```bash
# 좀비 PID에 직접 SIGKILL을 보내도 아무런 반응이 없습니다.
kill -9 15

# 여전히 좀비가 남아 있는지 확인
ps -eo pid,ppid,state,comm | awk '$3=="Z"'
```

이제 해당 좀비의 부모 프로세스(PPID)를 확인하고, 부모 프로세스에게 시그널을 전달하거나 상황을 분석합니다.

```bash
# 좀비 프로세스의 부모 PID(PPID) 확인
ps -o ppid= -p 15

# 부모 프로세스가 정상 서비스 중이므로 임의 종료 대신, 
# 애플리케이션의 리셋 엔드포인트를 호출하거나 적절한 부모 프로세스 갱신을 수행합니다.
```
